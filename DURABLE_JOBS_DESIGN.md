# Durable jobs design — Phase 2

**VERIFIED internal fixtures; real generation remains disabled.** Job schema v1 is additive inside the workspace-bound private identity SQLite store. Existing runs/history SQLite is unchanged. `Jobs` migration checks its own schema version and creates only new job/event tables. No previous job tables existed.

The fixed operation is `offline_release_preflight`: canonical source/task/config/plan/policy checking, a durable work reservation/checkpoint and an INCONCLUSIVE assessment. It cannot import a supplied callback/provider, run shell commands, accept a model operation or produce ACCEPT. COMPLETED means that offline operation finished, not a safe knowledge release. Existing legacy trusted-local evaluation remains operational. This is a real persistent offline worker, not certified durable native generation.

Lifecycle: CREATED → QUEUED → CLAIMED → RUNNING → COMPLETED/FAILED/INCONCLUSIVE. CREATED and QUEUED are committed together. Cancellation can produce CANCELLED before claim or CANCEL_REQUESTED after claim. Acknowledgment after reservation produces INCONCLUSIVE with unknown usage; before reservation it can produce CANCELLED. Terminal states cannot restart. Each transition appends a persisted event with timestamp and fence. Partial results remain separate from terminal results.

Submission is one BEGIN IMMEDIATE transaction: verify active operator/admin, check scoped idempotency, verify receipt/live reviewer, insert job/events, consume receipt and write submission audit. An interrupted transaction rolls everything back. Idempotency scope is workspace store + actor + operation + key; its digest covers payload, plan/receipt, source/task/config identities, policy and deadline. Same key/same inputs returns the existing job, including after restart; changed payload conflicts. Changed live inputs reject rather than reuse. Returning an existing job does not dispatch or renew authority; claim/reservation and terminal commit recheck authority. Revoked existing jobs can still be inspected; they cannot use that inspection to execute.

An atomic claim assigns a unique caller-provided worker ID, increments a fence, and sets a 1–60 second lease (default 15), capped by the job's total deadline (1–300 seconds including queue time). Heartbeats require current ownership and cannot extend the deadline. Stale owners cannot checkpoint/finish. A second process cannot claim active work. Expiry is not a generation permit: recovery terminalizes claimed work as CANCELLED before reservation or INCONCLUSIVE afterward, increments the fence and never requeues it. A fresh explicit operator action would require a new reviewed request/receipt; no automatic retries exist.

Queued capacity is 100 nonterminal jobs. Result/checkpoint JSON is bounded to 1 MiB. Job payload digests are checked when decoded. Input/version validation occurs before submission and before/after offline worker execution. Clock timestamps are local wall time; trusted system-clock administration is part of the single-host boundary. No multi-host lease protocol is claimed.

API: authenticated operator/admin POST `/api/v2/jobs` with `Idempotency-Key`, exact `specification`, `approval`, optional `max_seconds`, and operation `offline_release_preflight`. GET `/api/v2/jobs/{id}` returns its state/events only to its submitting actor or admin. POST `/api/v2/jobs/{id}/cancel` has the same ownership restriction plus mutation role. Existing session/CSRF controls apply. No API request starts a hidden worker; client disconnect does not undo a committed queue row. All original generation routes remain 403 in authenticated mode.

Foreground worker: `python -m sourceroi --project /workspace job-worker-once`. It handles at most one job and exits. `job-recover` seals expired ownership without restarting anything; `job-status --job-id ID` inspects a job. The OS administrator operates these commands; this is not a public worker service. Worker startup/shutdown is explicit; no daemon/supervisor was installed.

Guarantee: transactional single creation/receipt use per idempotency binding, one current fenced owner, and no automatic replay after ownership loss. **Not exactly-once external effects.** A reservation says work may have begun; a lost terminal result means unknown, not zero usage or success. Native permit/request/token accounting must still be integrated/tested behind separate generation authorization and Phase 3 gates before real dispatch is possible.

Receipt revocation is a separate additive table, not inferred from the consumed flag. Password reset, disable and even same-role administrative changes persist revocation. Submitting-actor credential revisions are bound into payloads and rechecked at reservation/commit; logout alone does not cancel an already submitted job.
